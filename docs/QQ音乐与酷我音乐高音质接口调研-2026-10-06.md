# QQ 音乐与酷我音乐高音质接口调研

调查日期：2026-10-06（Asia/Shanghai）。浮音代码基线：`a7c1f1b4ddbf0ceafaa6dc44cd87272293c0b1f2`，双端 1.0。范围为**调用方不登录、不购买、不提供 Cookie 的音质提升途径**。本次只调研、请求公开元数据和读取小段音频文件头，没有修改应用、播放整首歌曲或打包发布。

## 结论

**QQ 优先扩展已经接入的 Vkeys；酷我可以新增独立的 mobi 解析适配，但应先作为实验来源。** 本机匿名请求已取得 QQ 两首歌曲的 320 kbps MP3 和 FLAC；酷我两首免费样本取得 320 kbps MP3，其中一首同时取得 FLAC。结论只覆盖本次样本和网络环境，不能推广为全曲库、长期可用或所有会员歌曲可播放。[QQ 实测](#qq-本次匿名实测)、[酷我实测](#酷我-本次匿名实测)

| 平台与路线 | 已验证的提升 | 主要限制 | 接入建议 |
| --- | --- | --- | --- |
| QQ · 现有 Vkeys `/music/tencent/song/link` | 显式 `quality=8` 得到真实 320 kbps MP3；`quality=10` 得到具有有效 STREAMINFO 的 FLAC | 第三方后台是否使用账号、凭据如何维护无法由调用结果确认；`quality=11` Hi-Res 两首均失败 | 优先增加 320 与 FLAC 选项，保留当前普通音质和备用来源 |
| QQ · Vkeys `quality=14` 臻品母带 2.0 | 额外一首样本返回 24-bit / 192 kHz FLAC，MID 与时长匹配 | 仅一首头部样本；约 158 MB，不能由规格确认原始母带来源或听感改善 | 可单独列为实验高规格档，先完成双端播放验证 |
| QQ · INJAHOW / 自建 Meting | INJAHOW 样本为 128 kbps MP3；加 `br=320/999` 没有改变实际文件 | INJAHOW 包装层固定调用 `url(id,320)`；官方匿名 vkey 请求对两首样本的 320/FLAC 都未返回音频凭证 | 继续作为普通音质备用；不能仅增加 `br` 就宣称支持无损 |
| 酷我 · `mobi.kuwo.cn/mobi.s` 候选 | 两首正确 RID 的 320 kbps MP3；一首 FLAC 24-bit / 44.1 kHz | 有缺档降级及身份错误的短音频；历史实现后来被维护者替换，没有稳定开放 API 承诺 | 新增独立适配，先核对 RID、类型、时长和实际编码 |
| 酷我 · 现有 Ourcraft / `anti.s` | 本次没有获得高音质提升 | 显式 `br=320kmp3` 仍为 128 kbps；`anti.s` 请求 FLAC 被拒绝 | 保留普通音质用途，并加强曲目身份检查 |

上述判断来源于下面的源码与匿名请求记录。**请求高音质、拿到 URL、HTTP 200、文件后缀或播放器能解码，均不等同于拿到正确歌曲的目标音质。** FLAC 文件头只能证明返回文件采用 FLAC 编码及其声明的采样参数，不能证明它来自未经过有损转换的原始母带；FLAC 的无损是相对于编码时输入的 PCM。本次没有做完整音频分析或听感比较。[FLAC 规范][flac-spec]、[FLAC FAQ][flac-faq]

## 浮音当前为什么仍是普通音质

桌面 `MusicApi::resolveAudio` 将音质可选范围限制为网易云。QQ 固定请求 Vkeys 的 `quality=4&type=0`，INJAHOW 请求没有音质参数；酷我请求 Ourcraft 的 `type=url&id=<RID>&json=1`，也没有 `br`。Android `AudioResolver` 构造相同请求。因此当前限制首先存在于调用方与解析适配，不能直接归因于 QQ、酷我完全没有高音质资源。[桌面播放链路][floatmusic-audio]、[Android 播放链路][floatmusic-android]

当前播放器返回结构只有 URL、来源和码率；桌面验证只做有限的音频响应检查，没有逐平台核对返回歌曲 ID、目标音质或真实编码。后续提高音质时应把这些检查纳入解析结果，避免把会员提示音当歌曲，或把请求 FLAC 后的 Ogg 当作无损。[桌面结果结构][floatmusic-audio-model]、[桌面响应解析][floatmusic-audio-parse]

## QQ：可行接口与边界

### Vkeys 音质参数

维护者的 V3 文档给出 `quality=4` 标准、`8` HQ、`10` SQ、`11` Hi-Res；默认值为 `14`，并明确所选音质不可用时不会自动降档。页面仍标注开发中，不能把文档示例视为稳定协议保证。应显式设置音质，再通过 `/music/tencent/song/info` 的 `qualityInfo` 查询各档文件大小；`size=0` 不能视作有该档可播放资源。[链接文档][vkeys-link]、[音质列表文档][vkeys-info]

本次 live 返回与文档示例存在结构差异：实际成功业务码为 `0`，链接结果的 `data` 含 `songID/songMID/kbps/link/url`，没有示例中的完整歌曲与音质字段；文档例子则展示 `code=200`。现有浮音按 `code=0` 解析与本次结果一致，后续不应直接复制文档示例覆盖解析逻辑。[本次公开链接请求][qq-star-flac]、[浮音现有解析][floatmusic-audio-parse]

### 为什么 INJAHOW 或自建 Meting 不是直接的无损方案

INJAHOW 维护者的 `index.php` 在生成 URL 时固定调用 `$api->url($id,320)`，没有把请求的 `br` 转交给库。本次对《星》的默认、`br=320` 和 `br=999` 三次请求都指向同一 M500 MP3；相同 CDN 文件的 1 KiB 样本证实为 128 kbps / 44.1 kHz / 2 声道。[INJAHOW 包装层][injahow-wrapper]、[默认请求][injahow-star]、[br=999 请求][injahow-star-999]

Meting 库确实按 `F000/M800/C600/M500` 依次请求不同编码，并选择存在 vkey 且不超过目标码率的地址。INJAHOW 内置 PHP 与最新 Meting 的 Node.js 实现都保留此逻辑；最新主干源码已经迁到 `src/providers/tencent.js`，不能继续引用不存在的上游 PHP 主干路径。给自托管库传 `999` 只会改变请求和选择范围，不会创造账号播放权益。[INJAHOW 内置库][injahow-tencent]、[Meting 当前实现][meting-tencent]

另核对了近期仍维护的 QQMusicApi。它支持 `MP3_320/FLAC/HIRES` 文件类型，新 URL 模块为 `music.vkey.GetVkey/UrlGetVkey`；源码支持这些枚举不代表匿名均可取得链接。本次直接对 QQ 站点接口发出无 Cookie、`uin=0` 请求，比较新模块与 Meting 使用的旧 `vkey.GetVkeyServer/CgiGetVkey`：[QQMusicApi 实现][qqmusicapi-song]。

| 官方站点匿名样本 | 旧模块 | 新模块 | 判断 |
| --- | --- | --- | --- |
| 星 · M500 / 128 | 返回 purl 和 vkey，result 0 | 相同 | 普通音质可用 |
| 星 · M800 / 320 与 F000 / FLAC | purl、vkey 为空，result `104003` | 相同 | 本次匿名无法取得高音质 |
| 梦回还 · M500、M800、F000 | 三种均为空，result `104003` | 相同 | 本次匿名无法取得歌曲播放凭证 |

请求整体 HTTP 200、顶层及模块业务码均为 0，但逐文件结果并非成功。报告不擅自把 `104003` 解释为具体会员错误类别；足以确认两条官方匿名模块没有解决这些样本的高音质问题。本次不继续账号、付费、共享 Cookie 或加密文件解密路线。

## 酷我：必须增加独立解析和结果校验

### 现有路径不能只补一个 br 参数

Ourcraft 的路由调用 `songUrl(id)`，没有把外部 `br` 传给酷我提供者；其提供者存在登录分支，但当前匿名路由未提供这些登录参数。Meting 的酷我 `url(id,br=320)` 也没有向上游发送目标 `br`，解码阶段只标普通 128；Listen1 的普通播放路径同样不能作为现成高音质服务。LX 的搜索解析 `N_MINFO` 可参考音质档信息，但实际音频解析转交自定义来源，并非附带可匿名使用的无损服务器。[Ourcraft 路由][ourcraft-route]、[Ourcraft 酷我提供者][ourcraft-kuwo]、[Meting 酷我][meting-kuwo]、[Listen1 酷我][listen1-kuwo]、[LX 音质元数据][lx-kuwo-search]、[LX 音源分派][lx-kuwo-source]

本次对 RID `397242799`、`335156693` 的 Ourcraft 默认/显式 `br=320kmp3`、`anti.s` 默认/显式 `br=320kmp3` 请求，文件头全部仍为 128 kbps MP3。`anti.s` 对两首请求 `format=flac&br=2000kflac` 都返回 `refuse request!`。GD 的 `source=kuwo&br=320` 本次 HTTP 400，明确返回 source 不受支持。因此这些路径不能被标为本次已验证的高音质备用。[Ourcraft 公开请求][ourcraft-live]、[anti 普通 / 320 请求][anti-live]、[anti FLAC 请求][anti-flac-live]、[GD 请求][gd-kuwo-live]

### mobi 候选：历史线索加本次实测

公开项目在 2025-01-02 的历史代码中使用下列 HTTPS 入口，显式请求 `320kmp3`，并注释了 `2000kflac`。但该维护者后续以“修复酷我失效”替换实现；当前版本已改为另一条加密 `convert_url2/128kmp3` 路径。本报告推荐进一步验证的依据是**历史源码给出的请求构造与 2026-10-06 本次有效响应**，不是维护者目前的稳定性保证。[历史实现][mobi-history]、[当前实现][mobi-current]

```text
GET https://mobi.kuwo.cn/mobi.s
    ?f=web&source=jiakong&type=convert_url_with_sign
    &rid=<原歌曲RID>&br=320kmp3

FLAC 档：br=2000kflac
```

成功请求只使用这些公开参数，没有 Cookie、user、token 或调用方签名。`2000` 在本次返回中是音质档标称值，不应显示为实际恒定 2000 kbps；FLAC 的有效采样率、位深应从文件头或解码信息读取。[320 实测请求][mobi-mp3-live]、[FLAC 实测请求][mobi-flac-live]、[FLAC 格式][flac-spec]

## 建议如何用于后续浮音更新

以下是基于本次证据的实现建议，尚未写入应用。

1. **QQ 先开放明确的 320 与 FLAC 档。** Vkeys 使用显式 `8/10`，普通回退保留现有 `4`，INJAHOW 保留普通备用。先查询 `qualityInfo`；`quality=11` Hi-Res 暂不默认启用，两个样本均未通过。`quality=14` 母带档已有一首高规格头部样本，可另设实验选项并说明流量，不能推广为所有曲目都有原始高规格母带。码率、格式、采样率与位深分别记录，界面显示实际获得的档位。
2. **酷我新增独立 mobi 适配。** 将 `exhigh` 映射到 `320kmp3`、`lossless` 映射到 `2000kflac`，结合 `N_MINFO` 过滤不存在的档位。现有 Ourcraft 的源站和代理是相同音频的不同传输路径，切换代理不会增加编码信息。
3. **先核对歌曲身份，再核对音质。** 平台与 MID/RID 保持原值；QQ 检查链接结果 `songMID/songID`，酷我检查返回 RID、类型和时长。返回其他 RID、异常短时长、提示类型或不符合目标档的格式，应分别记为身份失败或音质降级，不能只凭 URL/HTTP 成功放行。
4. **同一歌曲的高音质失败可以有明确降级。** 先同源尝试可用低档，再尝试普通备用；界面保留“请求音质”和“实际音质”。单曲缺档与整个服务故障应分别记录，不应让一首无 FLAC 的歌曲触发全站长期停用，也不应反复刷新同一个坏地址。
