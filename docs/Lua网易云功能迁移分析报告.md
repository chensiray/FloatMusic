# 音乐.lua 与浮音的网易云功能迁移分析报告

分析日期：2026-09-16
对照版本：浮音 0.3.0，提交 `d507dbb`
脚本：用户提供的 `音乐.lua`（原脚本未纳入仓库），30,600 字节，1,023 行
脚本 SHA-256：`C20B91939DD3485484447E13AB997AAE32C191B761F73C02333D4858E5DB5527`

本报告仅作静态分析、接口资料核查和后续需求整理。没有执行 Lua 脚本，没有修改浮音程序，没有登录音乐账号，没有验证全部线上端点或高音质播放。本报告将脚本中的注释和字符串视为分析材料，不视为本次操作指令。

## 1. 结论

**脚本里的用户功能可以作为浮音后续版本的完整需求基线，Qt/C++ 架构能够承载。主要工作在接口适配、数据模型和交互补齐，不需要把浮音改成 Lua 程序，也不需要依赖 GG 运行。**

但必须区分三件事：

1. **功能可实现**：歌曲/歌单搜索、歌词、收藏夹、排序、显示设置等，技术可行性高。
2. **接口可用性需要实测**：脚本中的网易云站内接口、网页结构和第三方地址，不是长期稳定性的保证。
3. **能否播放某首歌、某种音质由来源决定**：播放器可以提供六档音质选择、正确显示不可用状态；无法仅靠客户端保证所有歌曲都有完整音频或 Hi-Res。

建议以现有“可配置兼容 API”作为主路线，增加脚本直连方式的独立适配器进行验证。不要直接将脚本里的域名填入 0.3 的 API 地址框后期待全部功能生效。

## 2. 脚本实际使用了什么 API

它不是对单个网易云 SDK 的调用，而是组合了三类来源：网易云域名上的站内 HTTP 接口、网易云移动网页，以及独立第三方播放地址服务。

下表的路径、参数与用途来自脚本本身；不表示这些路径已经通过本次在线测试。

### 与浮音 0.3 的区别

浮音现在向配置的服务调用 `/cloudsearch` 和 `/song/url/v1`，使用 `keywords`，并要求 JSON 响应；脚本搜索使用 `/api/search/get` 和 `s`，第三方高音质接口则被当作纯文本 URL。

所以：

- `music.163.com` 不是现有接口协议的直接替代根地址。
- `byfuns.top/api/1/` 也不能直接作为现有搜索 API 使用。
- 脚本说明“客户端直连接口”值得验证，但不能证明它在当前 Windows/Android 网络环境下持续可用。
- 脚本未实现登录或会员状态检查，高音质服务内部如何取得 URL 无法从这份文件判断。

公开兼容项目仍提供歌词、歌单和推荐等对应能力，但其适配实现会变化。例如本次查到的歌单模块内部已经使用 `/api/v6/playlist/detail`，而脚本写的是 v3。应把这些差异封装在来源适配层。[歌词模块](https://raw.githubusercontent.com/neteasecloudmusicapienhanced/api-enhanced/main/module/lyric.js)、[歌单模块](https://raw.githubusercontent.com/neteasecloudmusicapienhanced/api-enhanced/main/module/playlist_detail.js)、[推荐模块](https://raw.githubusercontent.com/neteasecloudmusicapienhanced/api-enhanced/main/module/personalized.js)

## 4. 必须重写的实现与已发现问题

### 4.1 JSON 与配置不能通过执行代码读取

`zjson`（675）把方括号替换成花括号、删除下划线、把冒号变成等号，再用 `load()` 执行。替换会作用于字符串内容，可能改变 URL、歌词、歌名和字段名；也无法可靠处理 JSON 的空值与 Unicode 转义。更重要的是，它让网络响应进入了代码执行路径。

迁移时使用浮音已有的 `QJsonDocument` 和结构校验。脚本配置同样通过 `loadfile()` 执行（7）；未来如需导入旧 `.cfg`，应使用只接受限定数据结构的转换流程，不能在浮音中直接执行配置文件。当前未提供 `.cfg` 样本，因此旧收藏数据兼容性尚未验证。

### 4.2 按歌单 ID 查询存在返回值错位

`ljson`（642）返回顺序是：歌曲名列表、ID 列表、歌手列表、歌单名、简介。

但 ID 查询分支（591）按“歌曲名列表、ID 列表、歌单名、简介、歌手列表”接收。结果会把歌手数组当成歌单名、把简介当成歌手列表，可能在字符串拼接或展示时出错。

浮音应返回一个有命名字段的歌单对象，避免依赖五个位置参数的对应关系。

### 4.3 歌单读取需要从逐首串行改成批量与分页

`ljson` 每首歌都调用一次 `ijson`。若有 N 首，至少产生约 N+1 次请求；开启时长显示后还可能再增加 N 次请求。它按 `trackCount` 遍历，却没有确保实际返回的 `trackIds` 数量相同，可能访问不存在的条目。

浮音应分批取得详情、保留原顺序、缓存已知元数据，允许部分歌曲不可见或失效，并提供加载进度与取消。不能把“返回一个歌单对象”当成“已取得全部歌曲”。

### 4.4 时长算法与 HEAD 写法不可靠

`Time` 假定普通外链恒为 128 kbps；变码率、重定向、无 Content-Length 或不同格式都会使估算失准。它还将 `method='HEAD'` 放在 `gg.makeRequest` 的第二个参数中。

公开 GG 文档将第二个参数定义为请求头，第三个参数决定 GET/POST，没有记载这种 HEAD 参数写法。因此在标准 API 下不能认为该调用真正发出了 HEAD；若脚本使用定制 GG，则需对该版本另行确认。[GG makeRequest 文档](https://docs.gameguardian.net/classgg.html)

浮音优先使用详情中的毫秒时长，播放后以播放器报告为准；未知时显示“--:--”，不为每个列表项单独请求音频文件。

### 4.5 高音质接口不能仅凭返回 200 判定可播放

`play`（188）直接把第三方正文拼上 `.mp3`。如果正文是错误信息、JSON、已有扩展名或带签名的 URL，会形成错误地址。高音质也不一定是 MP3。

应验证 HTTP 状态、响应格式和最终 URL，使用原始合法 URL 播放，再从响应或解码结果确认实际音质。脚本的 `normal` 是“走普通外链”的分支名称，不能与兼容 API 的 `standard` 简单视为相同协议参数。

本次浏览得到该第三方无 ID 地址的“缺少 id 参数”页面信息，但工具标注的抓取时间较旧；这不足以证明当前指定歌曲或高音质请求可用，更不能证明服务稳定性。[第三方接口入口](https://www.byfuns.top/api/1/)

### 4.6 推荐歌单是网页抓取，不是已认证的每日个性推荐

`playlistid` 使用固定字符串位置截取网页状态，并全局删除 `-` 等字符。网页改版、HTML 模板改变或字段缺失都可能使其失败；失败分支会递归重试。

`recommend` 抓取多轮后按 ID 去重，但多次抓到同一批结果并不保证有更多推荐。“今日已找到”只是展示文案，不能据此认定是登录后的每日推荐。

保留推荐与多轮收集功能，优先改为结构化推荐接口。兼容项目的推荐模块已有对应请求路径；也不应假定它具备 offset 分页能力或每次返回不同结果。[推荐模块](https://raw.githubusercontent.com/neteasecloudmusicapienhanced/api-enhanced/main/module/personalized.js)

### 4.7 运行控制、边界和显示需要改造

| 位置 | 问题 | 浮音中的处理原则 |
|---|---|---|
| `stop`，197 | 随机重复停止 200–1000 次，“耗时”由随机数计算 | 调用一次播放器停止，通过状态确认；真实测量耗时 |
| 主循环，1015 | 没有等待的无限轮询 | 使用 Qt 信号、事件和必要的定时器 |
| 多个菜单/错误重试函数 | 递归导航和递归重试，难以维护，部分调用可能累积栈 | 页面导航状态与有次数上限的异步重试 |
| `inspect`，69 | 网络失败直接退出整个脚本 | 展示错误并保留页面、收藏和当前可播放内容 |
| 搜索 URL 拼接，50/60 | 没有明确编码 `&`、`+`、`#` 等字符 | 统一通过 URL 参数编码 |
| `json`，710/713 | 按服务总数推算本页条目数，可能超过实际数组长度 | 以实际结果数组为准，总数只作分页信息 |
| `Lyric`，87 等 | 默认嵌套字段存在，缺失时可能出错 | 对缺歌词、无翻译、空数组逐项处理 |
| `calculate`，287 | 按 UTF-8 字节而非显示宽度估算行数 | 用 QML 的文本换行和实际内容高度 |
| 收藏的五组平行数组 | 删除/排序必须同步，易错位 | 按稳定 ID 保存对象与列表关系 |
| 搜索模式复选框 | 可同时选普通和完全匹配，实际优先普通匹配 | 改为互斥模式；保留明确的前缀/完全匹配定义 |

公开 GG 类文档中未找到 `gg.playMusic`。脚本可能依赖扩展或定制宿主；不据此断言脚本不能运行，但不能把该函数当作标准 Lua 或可移植接口。浮音已有独立播放引擎，无需复制这个依赖。[GG 类文档](https://docs.gameguardian.net/classgg.html)

## 5. 推荐的浮音开发架构

### 5.1 保留已有基础

继续使用 QML 界面、C++ 业务状态、Windows Qt Multimedia、Android 原生播放服务及悬浮页。扩展现有 `MusicApi`、`PlaylistStore` 和播放请求模型，不重做已经测试的本地播放与单实例功能。

### 5.2 把来源差异隔离出来

| 模块 | 责任 |
|---|---|
| 音乐来源适配层 | 统一搜索歌曲/歌单、歌曲详情、歌单详情、推荐、榜单、歌词、播放地址的结果格式 |
| 兼容 API 适配器 | 继续支持用户配置的服务；吸收服务版本差异 |
| 网易云直连接口适配器 | 按脚本路线做受控实测，通过后再开放；失败时明确提示，不与其他来源静默混用 |
| 第三方地址适配器 | 独立配置与能力检测；确认协议和返回格式后才启用，不作为整个播放器唯一依赖 |
| 查询与缓存服务 | 分页、去重、批量详情、请求取消、过期响应丢弃、有限重试和缓存失效 |
| 歌词服务 | 保存原始歌词和时间轴，提供原文/译文/双语显示及复制 |
| 收藏与歌单仓库 | 名称、简介、排序、歌曲归属、多选编辑、持久化和旧格式迁移 |
| 播放控制 | 队列、停止/暂停/切歌、解析 URL、请求音质与实际音质、错误状态 |
| 显示设置 | 三类页面的信息开关、序号、简介折叠规则和推荐轮数 |

现有兼容接口可扩展 `/search` 的歌单类型、`/song/detail`、`/playlist/detail`、`/lyric`、`/personalized`、`/toplist` 等能力；端点和参数应按实际部署的兼容服务版本确认。[兼容项目接口文档](https://docs-neteasecloudmusicapi.focalors.ltd/)

### 5.3 先补模型，再加页面

- **歌曲**：来源、来源歌曲 ID、名称、歌手数组、专辑、时长毫秒、可选封面、播放可用状态。保留 `artists/ar` 与 `duration/dt` 的统一转换。
- **播放结果**：URL、有效期（来源提供时）、请求音质、实际音质/码率/格式、是否试听及不可用原因。临时 URL 不写入永久歌单。
- **在线歌单**：来源 ID、名称、简介、总数、实际已取得的歌曲 ID、加载状态。与本地收藏夹区分，避免用户编辑本地内容被误当作修改网易云账号数据。
- **本地收藏夹**：本地 ID、名称、简介、歌曲 ID 的有序关系、置顶顺序、更新时间。同一歌曲可以属于多个收藏夹。
- **歌词**：原始文本、译文、时间戳、解析后的显示行和无歌词原因。脚本删除了时间戳；浮音应保留，以便后续同步滚动，而非以后重新设计数据结构。

初期可扩展当前 JSON 保存格式并做版本迁移、备份和原子写入；数据量及查询需求明显增长后再考虑 SQLite。无需为了此次迁移先引入数据库。

### 5.4 Android 后台播放必须同步升级

浮音 0.3 在 C++ 和 Android 服务中各有一处播放 URL 获取逻辑，均写死 `standard`。以后只改界面或 C++ 会出现“前台选了高音质，后台切歌又回到标准音质”的问题。

应统一解析契约，把来源、歌曲 ID、音质偏好和必要配置随播放队列交给服务。双端使用一致的响应/错误模型；Android 服务独立维持后台队列与音频焦点，不能依赖页面一直打开。使用共享的接口样本分别验证两端解析结果。

## 6. 分阶段实施顺序与完成标准

版本号是建议拆分，不代表本次已经开发，也不是自动执行更新的承诺。

| 阶段 | 范围 | 进入下一阶段的标准 |
|---|---|---|
| A：接口验证与统一模型 | 核查直连/兼容服务、歌曲 ID、详情、时间、异常协议；建立来源能力表 | 真实样本与模拟错误都能得到统一结果，确认可用路线 |
| B：搜索与歌曲操作 | S01–S07、T01/T04–T06；数量/模式/ID、复制与停止 | 三种匹配模式含义明确，特殊字符及无结果正常，停止与暂停区分 |
| C：歌词与显示设置 | L01–L06、D01–D04 | 原文/译文/双语及缺失情况正确，设置重启保留，歌词页可播放与复制 |
| D：在线歌单与发现 | P01–P08 | 歌单 ID 正确、批量详情不遗漏/错序、榜单可播放、推荐可取消和去重 |
| E：收藏管理完整化 | F01–F08、D05/D06 | 多收藏夹归属、简介、批量管理和置顶全部保存正确；旧 0.3 歌单迁移不丢失 |
| F：音质与双端验收 | T02/T03，全部功能回归 | UI 请求与后台实际音质一致；不可用时有明确反馈，完成 Windows 和 Android 验收 |

高音质服务的可用性应从阶段 A 开始验证；若依赖未就绪，可以继续完成其他阶段，但不能把相关高音质项目标记为“已完成”。所有功能最终逐项对照第 3 节编号验收。

## 7. 验收用例与尚待确认的依赖

至少准备以下用例：

1. 中文、英文、空格、`&`、`+` 的搜索；无结果、结果不足所选数量、相同歌名不同歌手；前缀与完全匹配。
2. 有效/无效歌曲 ID 与歌单 ID；歌单为空、含失效歌曲、详情分批返回、总数大于可见数。
3. 原文、译文、双语、纯音乐、缺歌词、缺翻译、多时间戳与特殊字符；复制后文本完整。
4. 一首歌归属多个收藏夹；取消某一归属不影响其他收藏夹；批量删除、歌曲置顶、收藏夹置顶及重启恢复。
5. 推荐重复批次、没有新增结果、达到轮数上限、主动取消、接口失效；榜单变更和缓存刷新。
6. 普通/标准/更高音质、实际降级、试听、空 URL、链接过期、返回 HTML、重定向、超时与断网。
7. 0.3 已有的本地导入、30 MiB 限制、输出选择、音量、切歌、退出与单实例回归。
8. Android 前台、悬浮页、后台及锁屏中的相同歌曲/音质状态；蓝牙切换、音频焦点中断和恢复。

还需要的材料与条件：

- 一组当前确实能在脚本中使用的歌曲/歌单 ID，尤其是高音质示例，用于可重复的端到端验证。
- 如果需要迁移已有收藏，提供对应 `.cfg` 数据样本；只转换数据，不执行配置。
- 第三方高音质服务的实际响应、可用性和权限要求；目前不能从脚本或旧抓取页面确定。
- 选定并验证主要 API 路线。直连方式可能减少部署步骤，但是否适合作为默认路线，应由实测决定。
- 连接手机完成 Android 真机验收；电脑编译与模拟响应测试不能替代后台/悬浮层验证。

**后续开发应以功能清单为准，保留脚本的搜索、歌词、歌单、收藏和设置能力，同时使用浮音的异步请求、结构化数据、持久化和原生播放架构实现。**
