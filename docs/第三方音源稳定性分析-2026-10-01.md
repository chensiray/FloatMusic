# 第三方音源稳定性实验与改进建议

日期：2026-10-01，约 12:10–12:19（中国标准时间）。浮音版本 `0.8.0-preview`。用户反馈歌曲“Coll Forset Rain”、Hi-Res、HTTP 523。本次完成实验与方案分析，没有修改播放器的请求、重试或音源策略。

后续 `0.8.0-preview.1` 已接入 GD 音乐台与 INJAHOW，并实现有限回退和故障冷却；见[备用音源接入与实测](备用音源接入与实测-2026-10-01.md)。本文保留接入前的诊断证据，以下“当前实现”指当时版本。

## 结论

本轮播放地址获取失败的主要证据指向默认第三方服务 `www.byfuns.top` 的源站连接故障：独立 Qt 探测的 **12 次音源请求全部未获得地址，其中 11 次 HTTP 523、1 次超时**。五档音质、多首歌曲、重复请求及客户端标识对照均未恢复；已经在解码开始之前失败。

响应包含 `Server: cloudflare`，新探测记录的 CF-Ray 节点为 HKG。Cloudflare 官方将 523 定义为无法联系源站，常见原因包括源站 IP/DNS 配置或 Cloudflare 到源站的路由问题。这说明问题发生在服务端链路；仅凭客户端实验无法进一步确定服务器停机、路由还是具体配置原因。[Cloudflare 523 文档](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/error-523/)

这不是“Hi-Res 音频格式不受支持”的证据。所有请求都尚未获得音频 URL，播放器还没有机会读取或解码音乐。本次结果也不能证明该服务永久停用、所有地区同时失败，或手机上的其他失败均由同一原因造成。

## 实验方法与结果

独立 Qt 工具直接请求服务，不读取浮音设置。保留原来的五档对照，补充 `--resolver-only`、限次复测、`Server`/`CF-Ray` 记录，以及单独搜索模式。原始结果放在本地忽略目录 `artifacts/playback-diagnosis-2026-10-01/`；没有下载整首音乐。

| 对照 | 次数 | 结果 |
|---|---:|---|
| 已有历史可播对照歌曲 `347230`，标准/较高/极高/无损/Hi-Res | 5 | 全部 HTTP 523，没有音频地址 |
| 《Cool Forest Rain》Dan Gibson 版本 `1220792`，Hi-Res/标准 | 2 | Hi-Res 为 523，标准在 12 秒限时内超时 |
| 同名 Northern Hemisphere 版本 `1913072131`，Hi-Res/标准 | 2 | 全部 HTTP 523 |

11 次 523 响应耗时约 2.5–10.3 秒。换音质仍调用同一主机，不能在源站连接故障时提供独立的备用路径。模拟 Android 标识不是手机真机网络测试；本次 ADB 未检测到手机。

按用户输入搜索后，最接近的标题为《Cool Forest Rain》，存在多个作者版本。用户没有提供作者或歌曲 ID，因此上表两版本用于对照，不能宣称已确认手机上点击的具体版本。

另外使用 Python 独立请求得到两次 HTTP 523，响应同样为 Cloudflare；该组仅作为交叉确认，不计入上表 12 次 Qt 样本。Python 搜索可返回 HTTP/业务 200，并得到上述同名歌曲，但其中一轮响应很慢。独立 Qt 搜索的两轮 12 秒限时请求均超时，记录为附加网络/响应延迟现象，没有将其忽略或计为通过。

应用测试环境的控制实验：

- `library_tests directPlaybackQualityAndLyrics liveRankings` 通过。浮音可从本地模拟 HTTP 音源播放、暂停、定位及切换音质；真实排行榜返回 63 个榜单，热歌榜完整读取 200 首。
- 新增显式联网测试 `liveResolveAudio`，直接调用浮音实际 `MusicApi::resolve("1220792", "hires", ...)`，约 15 秒超时，没有有效音频地址；测试按可用性断言失败，不能称为通过。它复现了地址获取失败，但这一轮没有收到 523。
- 增加诊断测试后，离线 API/播放测试再次运行，12 项通过、0 失败；3 项显式联网检查默认跳过，结果记录在本地日志。

真实服务的失败与离线回归通过是不同结论，前者不应被后者掩盖。

## 当前实现为什么容易反复失败

Windows `src/musicapi.cpp` 和 Android `PlaybackService.java` 默认都用 `https://www.byfuns.top/api/1/` 获取音频地址。更换音质只更换 `level` 参数。搜索、歌词、排行榜来自网易云元数据服务，所以“能搜索、能打开榜单，但无法播放”可以同时发生。

当前播放解析只发起一次请求，没有自动备用音源、服务健康记录、短时冷却或有限自动重试。手动重试会重新请求同一个主机。HTTP 523 的展示仍是通用错误文字，未明确告诉用户是音源服务的源站故障。反复换音质容易重复等待。

现有代码已经具备请求超时、加载代次保护和手动重试；获取新地址失败时尽量保留已加载的歌曲。下一步应扩展这些机制，避免在界面、解析器和播放器各自叠加重试。地址获取、音频下载和解码也应分别记录错误，避免将会员/权限、链接过期、网络中断和格式错误混为一类。

## 解决办法与优先级

### 1. 先让失败可理解、可退出

遇到 523 时显示“音源服务暂不可用（HTTP 523），稍后重试或切换服务”，保留歌曲和播放进度，允许取消。记录时间、服务主机、歌曲 ID、请求音质、阶段、HTTP 状态、耗时和 CF-Ray；不记录完整签名音频地址或账号凭证。

该错误的根本修复需要服务维护者检查源站、DNS、路由等，浮音无法通过更换解码器或延长等待修复对方源站。当前可用的应急办法是使用已有本地音频，或在设置中配置自己已经验证可用的兼容服务；没有实测备用服务时不能承诺更换一个免费接口即可解决。

### 2. 有限重试与服务冷却，缓解短时波动

建议只在地址解析层做自动重试，初始请求后最多重试一次，带随机延迟，并给整次播放请求设总时间上限。可把约 25 秒总预算、连续服务故障 3 次后冷却约 30 秒作为初始方案，具体数值需要后续测量调整，不是本次实验得到的最佳参数。切歌或取消必须停止旧连接和待执行重试，不能仅丢弃结果。

对临时超时及 502/503/504/部分 Cloudflare 5xx 可有限重试；429 遵循 Retry-After；明确的权限、无音源、无效歌曲和不支持的格式应直接说明。持续 523 时应减少无效请求，冷却后只放行一次恢复探测。重试需要次数和总时长上限，避免各层叠加造成请求放大。[AWS 限制重试建议](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_mitigate_interaction_failure_limit_retries.html)、[服务熔断模式](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/circuit-breaker.html)

这些措施能减少偶发失败和等待，不能在持续源站故障时创造可播放音源。

### 3. 引入独立备用音源，降低单点依赖

这是解决“主服务持续不可用仍希望在线播放”的关键。需要把元数据地址与音频解析来源分开，支持按优先级配置、实际验证可用的主备服务，并记录来源健康状态。现在自定义 API 根地址会同时切换元数据与音频接口，后续可允许只换音源、继续使用原来的搜索和歌单。

切换失败来源时保持歌曲 ID、请求音质、暂停状态和进度；服务故障应换来源，某来源没有该音质时才考虑降级。降低音质应由用户允许，并显示实际音质，不能把返回的标准 MP3 标成 Hi-Res。多个域名若仍共用同一解析后端，不能当作真正独立的备用服务。

备用来源应有明确接口契约、合理可用性和授权边界，不能靠不断堆叠未经验证的免费接口来承诺稳定。

### 4. 短期缓存成功地址，减少重复解析

只短时复用已验证成功的会话地址，遵循服务提供的过期信息；没有可靠过期时间时采取保守策略。音频地址返回 403/404 等失效状态时清除缓存，按当前请求重新解析一次，避免永久保存临时签名链接。错误结果不缓存为可用音源。

URL 缓存只能减少解析请求；音频 CDN 也可能不可用，而且不提供离线保障。完整音频缓存属于另外一项产品功能，需要单独考虑空间、清理和用户选择，不是本次已实现的方案。

## 建议实施顺序与验收

先完成错误分类、单层有限重试、取消和冷却，再接入独立备用音源；短期地址缓存随后加入。若必须在主接口持续失效时继续在线播放，应优先准备可验证的备用来源。

双端用相同策略和用例验证：一次 503 后恢复、连续 523、429、无音源、地址过期、音频解码失败、重试中切歌，以及主备均失败。验收应确认不会无限等待、不会切回旧歌曲、不会悄悄更改音质，已在播放的曲目不会因后台重试被打断。外部服务恢复后再补真实播放、暂停、进度定位和连续切歌实验。

本次只完成诊断工具、可重复实验和方案文档；上述容错策略尚未加入交付的 EXE/APK。
